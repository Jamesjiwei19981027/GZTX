# 02 - 技术架构设计文档

> 本文档描述工作待办提醒系统的整体技术架构、技术选型依据、以及部署方案。

---

## 一、架构设计原则

1. **简单优先**：避免过度设计，选择成熟稳定的技术
2. **渐进增强**：MVP阶段保持简单，后续逐步扩展
3. **前后端分离**：清晰的接口边界，便于多端开发
4. **云原生友好**：支持容器化部署，便于扩展
5. **开发友好**：热重载、类型提示、自动化测试

## 三、技术选型

### 3.1 后端技术栈

#### 核心框架：FastAPI

| 维度 | 选择理由 |
|------|---------|
| 性能 | 基于 Starlette 和 Pydantic，性能接近 Node.js 和 Go |
| 开发效率 | 自动数据校验、序列化、API文档生成 |
| 类型安全 | 原生支持 Python 类型提示，减少运行时错误 |
| 异步支持 | 原生 async/await，高并发场景表现优秀 |
| 生态 | 丰富的中间件和插件生态 |

**为什么不选 Flask/Django？**
- Flask：需要手动处理异步、数据校验，开发效率较低
- Django：过于重量级，ORM耦合度高，不适合API优先的项目

#### 数据库：SQLite → PostgreSQL

| 阶段 | 数据库 | 理由 |
|------|--------|------|
| 开发/MVP | SQLite | 零配置，单文件，便于开发和测试 |
| 生产 | PostgreSQL | 事务支持好，并发性能强，JSON字段支持 |

#### ORM：SQLAlchemy 2.0

- 成熟的 Python ORM，支持异步（async SQLAlchemy）
- 与 FastAPI + Pydantic 配合良好
- 数据库迁移工具 Alembic 配套成熟

#### 数据校验：Pydantic v2

- FastAPI 内置集成
- 性能比 v1 提升 5-50 倍
- 支持复杂的数据模型和验证规则

#### 任务调度：APScheduler

- 纯 Python 实现，无需额外依赖
- 支持多种触发器（日期、间隔、cron）
- 与 FastAPI 集成简单

#### 认证：JWT (python-jose) + Passlib

- 无状态认证，适合分布式和移动端
- Passlib 支持多种密码哈希算法（bcrypt）

### 3.2 前端技术栈

#### 框架：Vue 3

| 维度 | 选择理由 |
|------|---------|
| 学习曲线 | 比 React 更平缓，模板语法直观 |
| 性能 | 响应式系统优化，编译时优化（Vue 3.2+） |
| 体积 | 运行时体积小，首屏加载快 |
| 生态 | Element Plus、Pinia 等生态完善 |

**为什么不选 React？**
- React 更灵活但需要更多配置，Vue 3 的 Composition API 已经提供了类似的灵活性
- 对于中后台管理系统，Vue + Element Plus 开发效率更高

#### 构建工具：Vite

- 基于 ES Modules，开发服务器启动极快（< 300ms）
- 热更新（HMR）速度快
- 生产构建使用 Rollup，输出优化好

#### UI组件库：Element Plus

- 基于 Vue 3 的企业级组件库
- 组件丰富，文档完善
- 主题定制方便

#### 状态管理：Pinia

- Vue 官方推荐，替代 Vuex
- TypeScript 支持好，API 更简洁
- 支持组合式 API 风格

#### HTTP客户端：Axios

- 浏览器和 Node.js 通用
- 拦截器、取消请求等高级功能
- 请求/响应转换方便

#### PWA支持：Vite PWA Plugin

- 自动生成 Service Worker
- 支持离线缓存、后台同步
- 可安装到桌面

### 3.3 小程序技术栈

#### 框架：微信小程序原生

| 维度 | 选择理由 |
|------|---------|
| 稳定性 | 原生框架最稳定，文档最完善 |
| 性能 | 无框架层开销，包体积最小 |
| 微信特性 | 对新API支持最快 |

**为什么不选 Taro/UniApp？**
- MVP阶段功能不复杂，原生开发足够
- 避免跨端框架的兼容性问题
- 后续如需扩展多端，可再考虑迁移

#### 状态管理：MobX-MiniProgram 或自研简单 Store

- 小程序原生不支持复杂状态管理
- 根据复杂度选择轻量方案

### 3.4 部署与运维

#### 容器化：Docker + Docker Compose

- 开发环境一致性
- 一键部署，降低运维门槛
- 便于后续迁移到 Kubernetes

#### 反向代理：Nginx

- 静态资源服务
- SSL/TLS 终端
- 负载均衡（后续扩展）

#### 监控（可选）：Prometheus + Grafana

- API 性能监控
- 系统资源监控
- 自定义业务指标

## 四、数据流设计

### 4.1 正常请求流程

```
用户操作 → 前端发起请求 → Nginx → FastAPI → 业务逻辑 → ORM → 数据库
                                              ↓
用户看到结果 ← 前端渲染 ← JSON响应 ← 数据序列化 ← 查询结果
```

### 4.2 提醒任务流程

```
用户创建带提醒的任务
        ↓
APScheduler 注册定时任务
        ↓
到达提醒时间
        ↓
查询任务和用户信息
        ↓
根据用户偏好发送通知
   ┌────┴────┬────────┐
   ▼         ▼        ▼
Web推送   微信消息   邮件
```

### 4.3 数据同步流程

```
Web端修改任务
        ↓
调用 API 更新数据库
        ↓
返回最新数据
        ↓
小程序下次打开时拉取最新数据
        ↓
（可选）WebSocket 实时推送更新
```

## 五、安全设计

### 5.1 认证授权

```
用户登录
   ↓
验证用户名密码
   ↓
生成 JWT (Access Token + Refresh Token)
   ↓
Access Token: 15分钟有效期，存储在内存
Refresh Token: 7天有效期，存储在 httpOnly Cookie
   ↓
每次请求携带 Access Token (Authorization: Bearer <token>)
   ↓
Token 过期 → 用 Refresh Token 换取新的 Access Token
```

### 5.2 微信小程序登录

```
小程序调用 wx.login() 获取 code
   ↓
将 code 发送到后端
   ↓
后端用 code + AppID + AppSecret 请求微信接口获取 openid
   ↓
根据 openid 查找/创建用户
   ↓
返回 JWT Token
```

### 5.3 防护措施

| 威胁 | 防护措施 |
|------|---------|
| SQL注入 | 使用 ORM 参数化查询 |
| XSS | 前端转义输出，CSP策略 |
| CSRF | JWT无状态认证天然免疫，配合SameSite Cookie |
| 暴力破解 | 登录接口限流（5次/分钟） |
| 敏感数据泄露 | 密码bcrypt加密，HTTPS传输 |
| 接口滥用 | 全局限流（100次/分钟/IP） |

## 六、部署架构

### 6.1 开发环境

```
本地机器
├── Docker Desktop
│   ├── backend (FastAPI)     ← 热重载开发
│   ├── frontend (Vite dev)   ← 热更新开发
│   └── db (SQLite/Postgres)  ← 数据持久化
└── 微信开发者工具             ← 小程序开发
```

### 6.2 生产环境（单服务器）

```
云服务器 (2核4G)
├── Docker Compose
│   ├── nginx (80/443)
│   ├── backend (FastAPI + Gunicorn + Uvicorn workers)
│   ├── frontend (Nginx 静态资源)
│   └── postgres (5432)
└── 定时任务 (APScheduler 在 backend 容器内)
```

### 6.3 生产环境（扩展）

```
负载均衡器 (Nginx/云LB)
   ├── 服务器1: backend + frontend
   ├── 服务器2: backend + frontend
   └── 服务器N: backend + frontend
   
独立数据库服务器: PostgreSQL (主从复制)
独立缓存服务器: Redis
对象存储: 用户头像等静态资源
```

## 八、关键技术决策记录

### ADR-001: 使用 FastAPI 而非 Flask/Django

**背景**: 需要选择一个 Python Web 框架作为后端

**决策**: 使用 FastAPI

**理由**:
- 原生异步支持，性能更好
- 自动 API 文档（Swagger/ReDoc）
- 基于类型提示的数据校验
- 现代 Python 生态的标准选择

**影响**: 团队需要学习 async/await 模式

---

### ADR-002: 使用 SQLite 开发，PostgreSQL 生产

**背景**: 需要选择数据库方案

**决策**: 开发用 SQLite，生产用 PostgreSQL

**理由**:
- SQLite 零配置，便于快速启动开发
- SQLAlchemy 抽象了数据库差异，迁移成本低
- PostgreSQL 生产环境更可靠

**影响**: 需要确保 SQLAlchemy 配置兼容两者

---

### ADR-003: 使用 Vue3 而非 React

**背景**: 需要选择前端框架

**决策**: 使用 Vue 3 + Vite

**理由**:
- 开发效率更高，模板语法直观
- Element Plus 组件库成熟
- 与 TypeScript 集成良好

**影响**: 如果团队熟悉 React，需要适应期

---

### ADR-004: 小程序使用原生而非跨端框架

**背景**: 需要选择小程序开发方案

**决策**: 使用微信小程序原生框架

**理由**:
- MVP 阶段功能简单，原生足够
- 避免跨端框架的兼容性问题
- 包体积更小，启动更快

**影响**: 代码不能复用到其他平台小程序
