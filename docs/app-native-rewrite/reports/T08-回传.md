## 五、网页版通话能力的实际情况与原生方案

### 1. 网页版到底做到了哪一步（读代码结论）

- 手机网页版 `frontend/src/mobile/features/messages/MobileCallScreen.tsx`：
  - 只做三件事：`GET /calls/config`（读 STUN/TURN 配置）、`POST /calls/sessions`（有 `conversationId` 时创建会话）、`POST /calls/sessions/{id}/end`（关闭时结束会话）。
  - 界面只有“配置未就绪”诊断态和“信令已就绪，正在连接…”文案；**没有任何 `RTCPeerConnection`、麦克风采集、音频播放代码**，静音/扬声器按钮只改本地状态。
  - 因此网页手机版并不是“可通话”，只是“通话会话登记 + 配置体检”。
- 电脑版 `frontend/src/components/views/MessagesView.tsx` 另有：上传通话录音 → 转写 → AI 总结（`uploadCallRecording` / `transcribeCallSession` / `summarizeCallSession`）。手机版没有接这三步。
- 后端 `backend/app/api/v1/calls.py` 提供完整接口：ICE 配置、会话增删查、录音上传、转写、总结，以及 `/calls/ws/{conversation_id}` 信令 WebSocket。

### 2. 原生版本次实现（与网页手机版能力对齐）

- `GET /calls/config?company_id=`：真实展示“已配置/未配置”，未配置时给出诊断信息和“不显示伪造通话中”的说明。
- 有 `conversationId` 时 `POST /calls/sessions` 创建会话，页面显示会话编号；挂断/关闭/系统返回都会 `POST /calls/sessions/{id}/end`；结束失败会留在页面并给出错误，避免服务端留下悬空会话。
- 静音/扬声器只反映本地开关，不声称已建立媒体连接；页面明确写出“本安装包尚未接入实时音频采集与播放”。
- **录音/转写/总结未接入**：与网页手机版一致（该能力在电脑版）；如需补齐，属于通话能力扩展，不在本任务硬做。

### 3. 真正的双向语音方案（单独方案，不在本任务实施）

需要三块共享改动，缺一不可：
1. **依赖**：`flutter_webrtc`（含安卓 `RECORD_AUDIO`/`MODIFY_AUDIO_SETTINGS`、iOS `NSMicrophoneUsageDescription` 权限声明）。
2. **信令**：复用后端 `/calls/ws/{conversation_id}`，原生侧用 `web_socket_channel` 连接并转发 offer/answer/candidate；需要明确鉴权帧格式（后端首帧鉴权，10 秒超时）。
3. **穿透**：部署 TURN 并写入 `WEBRTC_STUN_URLS` / `WEBRTC_TURN_URLS` / `WEBRTC_TURN_USERNAME` / `WEBRTC_TURN_CREDENTIAL`；否则跨网段基本无法连通。
4. 还需要：音频路由（听筒/扬声器切换）、后台与锁屏策略、来电/振铃事件（后端目前只有会话状态，无呼叫邀请事件）、录音上传与转写（可选）。
建议作为 **T08b「实时语音」** 单独立项，先做 1 对 1 内网验证，再评估群聊与视频。

## 六、与网页版不一致之处（逐条说明理由）

1. **错误不再静默吞掉**：网页版大量 `catch { /* ignore */ }`（消息拉取、点赞、总结、通知列表等）。原生版按底座 `core/errors` 区分 `NetworkException / ApiException / AuthException / ValidationException`，给出可见错误、重试入口或无权限说明。
2. **外部邮件未配置的原因**：网页版把后端英文 `reason` 直接展示，且请求异常时伪造 `configured:false` 与假原因。原生版把英文原因转成中文，查询失败则显示“外部邮件状态查询失败 + 重试”，不伪造状态。
3. **未配置信令时不创建通话会话**：网页版无论配置与否都会 `POST /calls/sessions`。原生版仅在 `configured == true` 时创建——电话本来就打不通，登记一条通话记录会误导用户（也让“未配置”页面出现无关的会话错误）。
4. **频道内不发起通话**：网页版频道里也有通话按钮，但因为没有 `conversationId`，进去只会停在配置体检页且不产生会话。原生版保留入口但明确提示“频道通话暂不支持，请从私聊发起”，不制造假动作。
5. **附件在消息气泡内可见**：网页版聊天页只渲染消息文本，附件要到“会话资料”里找。原生版在气泡内展示文件名/大小，点击复制下载链接（可直接查看，需 `url_launcher`，见共享申请）。
6. **轮询边界更严**：网页版组件卸载才停止；原生版退到后台（paused/inactive/hidden）即停止，回前台补拉一次；首屏失败（尤其 403）也停止轮询，避免持续打一个打不开的会话。
7. **通知列表项自绘**：底座 `AppListTile` 的副标题在 iOS 上只显示一行，会把通知正文截断；原生版单独实现列表项（未读蓝点 + 发送人加粗 + 正文最多 3 行），与网页版“加粗 + 两行预览”对齐。
8. **“转任务草稿”未接**：网页版消息/通知/邮件都有“转任务待办草稿”，属于 T02 的草稿能力与跨模块回调；T08 目录内无法完成，已列入共享改动申请。
9. **AI 总结展示**：网页版只展示 `summary_text` 与来源条数；原生版同样展示来源条数与生成方式（`deterministic` → “事实规则摘要”），并补了生成中/失败重试状态。
10. **深色模式与极端尺寸**：网页版只有演示用的 `adapt-*` 页面；原生版把空状态、加载、失败、无权限、断网提示做成真实状态，并用测试覆盖 320/430/字号 200%/深色模式。

## 七、共享改动申请

1. **`app/pubspec.yaml` 增加 `file_picker`（与 T05 同一诉求）**：目前没有系统文件选择能力，`UnavailableMessageFilePicker` 只能给出“尚未集成，已提交申请”的明确提示。加上依赖后把实现替换为真实选择器即可，上传与消息绑定链路已实现并有测试（`_FakePicker` 注入验证了上传范围、文件编号、附件渲染）。

3. **`app/pubspec.yaml` + 平台权限增加 `flutter_webrtc`、`web_socket_channel`**：实时语音的前提（详见第五节），并需要 TURN 环境变量。

5. **公共文件选择/上传模块去重**：`features/evidence/data/multipart_transport.dart` 与 `features/messages/data/message_file_transfer.dart` 是同类实现（T05/T08 各自维护）。建议在 `core` 或 `design` 提供统一上传器，避免三处各写一份。
6. **跨模块“消息/通知转任务草稿”回调**：需要 T02 暴露草稿入口（网页版 `onConvertToTaskDraft`），T08 只负责提供消息文本与来源标记。

## 八、发现的接口问题

1. **测试账号没有企业数据（环境问题，阻塞真实联调）**：`e2e_user` 调 `/companies/mine` 返回空列表，因此频道、私聊、联系人、通话配置一律 403（`非公司成员` / `not an active company member`）。我用该账号只核对了错误信封与通知空列表，**没有**在真实数据上跑通频道/私聊/通话。集成阶段需要补一份“企业 + 项目 + 两个成员 + 一条私聊”的夹具。
2. **英文错误直出**：`external_mail.py`、`calls.py` 大量 `HTTPException(detail="...")` 为英文（`IMAP credentials are not configured`、`not an active company member`、`recording not found` 等）。前端只能自行映射；建议后端统一中文 + 业务码。
3. **没有单条会话接口**：`GET /conversations/{id}` 不存在，会话资料页只能拉全量会话列表再找成员（`N+1` 之外还多一次列表请求）；也没有“频道成员”接口，频道资料无法展示成员。
4. **频道无法发起通话**：`POST /calls/sessions` 必须传 `conversation_id`，而频道没有会话；网页版却给了通话按钮，形成“点了没反应”的入口。
5. **附件字段命名不一致**：消息 `attachments_json` 里是 `file_id`，而 `GET /channels/{id}/files` 返回的协作文件是 `id`；两处 `size` 字段也分别是 `size_bytes` / `file_size`（历史数据）。客户端已做兼容，但建议统一。
6. **协作文件上传接口的分页/上限**：`GET /channels/{id}/files` 里消息附件与二进制文件合并后截断 100 条，且非二进制附件没有 `id`（只有 `file_id`），做“下载”时需区分；已按字段兼容。
7. **通知只有 20 条分页且前端没有翻页**：`GET /notifications/collab` 默认 `page_size=20`，网页手机版与原生版都只取第一页，历史通知不可见（不是本次新增的问题，记录备查）。
8. **通话配置 `message` 为英文**：`GET /calls/config` 未配置时返回英文说明，原生版未直接展示该字段，改用中文诊断文案。
9. **会话列表性能**：`GET /companies/{id}/conversations` 对每个会话各查一次成员与最后一条消息（N+1）；会话多时移动端首屏会变慢。建议后端批量查询（本次不改后端）。

### 1. 消息 Tab 常驻时切换公司/项目仍查旧数据（P1，messages_root_screen.dart:55-61）

- **问题**：六个页面（消息首页、工作联系人、通知收件箱、会话资料、通话、会话）都在 `didChangeDependencies` 里用 `context.authStateRead`（即 `read`）取公司/项目。`read` 不建立 Provider 依赖，只要页面还挂着（消息 Tab 在 `StatefulShellRoute` 里常驻），切换公司或项目后 `didChangeDependencies` 不会重跑，控制器继续用旧 `companyId`/`projectId` 查询并展示，等于把上一个企业/项目的频道、私聊、联系人、通知、会话资料显示在新上下文下，违反项目隔离约定。
- **怎么改**：六处的 `context.authStateRead` 统一换成 `context.authState`（`watch`），在 `didChangeDependencies` 里建立依赖：登录态 `notifyListeners` 后该方法会重跑，`_resolve()` 按新的 `currentCompany`/`currentProject`/`currentUser`/`api` 比对，不一致就 `dispose` 旧控制器、按新参数重建并重新 `load()`；`widget.repository != null`（测试注入）时仍完全不走登录态。迟到结果由控制器自身的 `_disposed` 与 `seq` 校验丢弃：旧控制器已被 dispose，晚到的响应只写进已废弃对象，不会覆盖新列表。这与 `features/knowledge/screens/knowledge_screen.dart` 处理常驻 Tab 的写法一致。
- **哪个测试验证**：`messages_root_screen_test.dart` 新增“消息 Tab 常驻时切换项目：列表换成新项目数据，旧请求的迟到结果被丢弃”——用自定义 `MockClient` 让项目 7 的 `GET /companies/1/channels` **挂起**，挂载后 `auth.selectProject(8)`，断言请求按 `project_id=7 → 8` 发出、页面显示“八号项目的频道”、旧频道不出现；再放行项目 7 的迟到响应，断言页面仍是新项目数据、旧频道依旧不出现。把该文件的 `context.authState` 改回 `authStateRead` 复跑，此用例失败，确认能复现原缺陷。`work_contacts_screen_test.dart` 另加“页面常驻时切换项目：联系人改为新项目的数据”，覆盖同一模式在联系人页的效果。

### 2. 附件下载地址重复拼接 `/api/v1`（P1，chat_screen.dart:274-277）

### 3. multipart 上传绕过 401 续期（P2，message_file_transfer.dart:117-119）

- **问题**：上传用裸 `http.Client`，只把当前访问令牌塞进请求头。底座 `ApiClient` 的 401 续期和 `onAuthExpired` 都在 `_request` 内部，`_tryRefresh`/`_doRefresh` 是私有方法，multipart 用不上；访问令牌过期但刷新令牌仍有效时，上传直接 401 失败，令牌也不会刷新，页面停在“文件上传失败”。
- **怎么改**：在 `ApiMessageFileUploader` 内实现与 `ApiClient` 等价的续期规则（`core/` 未改）：上传收到 401 → 用 `refresh_token` POST `/auth/refresh` → 成功则保存新令牌（含轮换下发的新 `refresh_token`）并用新令牌重发一次同一份 multipart 字节（报文只构造一次）；重试后仍 401，或没有刷新令牌、刷新接口 401/403、网络异常时，清空凭证并调用 `_api.onAuthExpired`，抛 `AuthException('登录已过期，请重新登录')`，不再循环重试。续期用单飞 `_refreshInflight`，并发上传同时 401 时只刷新一次，避免轮换后的刷新令牌被重复使用。
- **哪个测试验证**：`message_file_transfer_test.dart` 新增三条：①“访问令牌过期但刷新令牌有效时，续期后重试一次并上传成功”（断言刷新请求体为 `refresh-1`、只续期一次、两次上传的鉴权头依次为 `expired-token`/`new-token`、新旧刷新令牌都已落盘）；②“续期被拒时清空凭证并触发登录过期处理，不循环重试”（上传只发 1 次、`onAuthExpired` 触发 1 次、凭证被清空、抛 `AuthException`）；③“没有刷新令牌时直接按登录过期处理，不再重发上传”。组件层原有的上传用例（`_FakeUploader` 注入、发送文件随消息提交文件编号）保持不变。
