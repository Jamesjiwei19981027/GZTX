# 从一个待办到总领导决策：产品完整故事

## 故事背景

周一早上，项目负责人王宁打开“烂笔头 PM”。他在电脑 Web 端登录，系统先完成账号、公司、项目、任务、分类、标签和界面偏好的同步。王宁上周换过电脑，但因为状态都保存在服务端，他看到的项目选择、未读通知、任务状态和人轴位置与手机上完全一致。

系统发现王宁的邮箱已经验证，但手机尚未验证。王宁准备创建新公司，页面弹出手机验证。系统先发送验证码，验证成功后自动继续刚才的创建动作，没有让他重新填写公司信息。公司创建完成后，他建立“客户交付项目”，选择自己为项目管理者，并邀请林悦、陈宇和赵敏加入。

## 第一幕：把目标拆成责任链

王宁进入人轴页面，选择“客户交付项目”。画布显示项目管理者、产品、研发、测试和交付节点。王宁点击“新增下级”，给林悦建立产品负责人节点，再给林悦添加陈宇作为研发下属。系统阻止把某个节点设置为自己的上级，也阻止形成循环关系。

他为每个节点填写岗位、部门、职责范围和可见权限。人轴保存后，系统把人员、岗位、上下级、任务范围和证据范围作为项目内的唯一事实来源。每个成员在这个项目里都有自己的个人智能体，项目根节点还有一个项目管理者智能体。王宁调整人轴关系时，新的汇报链会自动跟随新的直属关系，旧报告仍保留原来的路径和审计记录。

王宁点击“AI 审计”，系统检查是否存在没有负责人的节点、没有下属的管理节点、重复绑定和权限缺口。审计是后台任务，页面显示排队、运行、完成或失败状态，不会把尚未完成的审计伪装成成功。

## 第二幕：从一句话变成可执行任务

客户在群里发来一句话：“周五前完成接口联调，验收材料需要 API 文档和录屏。”王宁把这句话粘贴到“快速添加”。系统识别出任务标题、截止日期和材料提示，王宁在预览里确认后创建任务，并把任务绑定到研发节点。

林悦又在 Web 消息中心创建项目频道“客户交付”。她发送文本、Emoji 和一份需求文档。陈宇上传接口说明，赵敏在手机上补充测试环境地址。文件进入项目范围的协作存储，消息中的附件只保留可授权下载的引用。没有项目权限的用户即使拿到文件 ID，也无法下载。

王宁在看板中看到任务进入“进行中”。陈宇拖动卡片更新状态，赵敏在日历上把验收日期顺延一天。系统把这些动作写入任务、进度和活动记录。若有人误操作，任务可以恢复；重复任务完成后，系统按照重复规则生成下一实例。

## 第三幕：成员让自己的智能体准备汇报

周三下午，陈宇打开手机。他不需要写一份长报告，只需在 AI 汇报页面补充：“接口已经联调，测试环境仍缺少客户验收账号，周五需要确认上线窗口。”他的个人智能体读取本项目中他被授权的任务、证据、进度和这段主动输入，生成一份带来源的汇报草稿。

草稿中列出：

- 已完成：接口联调。
- 待办：确认客户验收账号和上线窗口。
- 风险：验收账号尚未提供。
- 来源：联调任务、接口文档、陈宇主动输入。

陈宇可以编辑文字、补充文件、删除不准确的表述，然后点击“确认提交”。提交后报告形成一个不可覆盖的版本。系统同时把“已提交”状态写入个人报告、直属领导收件箱和直属领导的项目智能体队列。

林悦的 Web 端收到未读通知，手机小程序也显示一条上级链路消息。她点开报告后，系统先标记已读，再展示陈宇的原文、来源和 AI 生成内容。林悦不需要重新整理陈宇的报告，她的项目智能体会把陈宇的汇报放进自己的项目上下文中。

## 第四幕：人轴链路继续向上汇报

林悦查看自己的职责范围和下属汇报。她看到陈宇已提交、赵敏缺少验收证据、另一个节点有一份过期报告。她可以点击“追问”，让自己的智能体向陈宇的智能体发送问题：“请在周四 18:00 前补充验收账号和录屏。”这条追问会沿着项目内的人轴关系写入陈宇的 AI 收件箱。

林悦随后提交自己的汇报。她的报告包含产品进展、研发进展、测试状态和需要王宁决策的事项。系统把报告送给直属领导王宁，同时把同一份内容送入王宁的项目管理者智能体。这里的人轴没有被智能体替换：智能体负责整理、提示和逐级转发，直属领导关系、权限和项目边界仍由人轴和后端决定。

## 第五幕：管理者对照资料，而不是只看口头汇报

王宁打开“项目汇报中心”，看到整个下属树的最新报告、缺失资料、冲突和风险。他点击“汇总项目汇报”。项目管理者智能体只读取这个项目的任务、证据、Wiki、进度和下属报告，生成项目级摘要：

1. 接口联调已完成，来源是任务状态和接口文档。
2. 客户验收账号缺失，属于阻塞风险。
3. 测试人员的报告称“已准备”，但没有上传录屏，标记为材料不足。
4. 周五上线窗口需要王宁确认。

王宁点击冲突项，看到“汇报说完成，但项目资料没有证明”。系统只标记差异，不自动把任务改成完成，也不自动采纳证据。王宁确认录屏已经上传后，才手动更新任务和证据状态。

他也可以在项目 Wiki 中生成草稿。Wiki 把任务、责任节点、证据和知识检索结果整理成项目说明，所有引用可以回到原始资料。王宁人工发布后，这份 Wiki 才成为项目正式知识。

## 第六幕：一次通话也成为可追溯资料

王宁和客户在私聊中发起语音通话。Web 端先创建通话会话，再通过 WebSocket 交换加入、offer、answer 和 ICE candidate。浏览器获得麦克风权限后，界面显示本地媒体状态和远端连接状态。通话结束时，系统关闭连接和媒体轨道，写入结束时间和参与者。

如果生产环境配置了真实 ASR，桌面端的 MediaRecorder 会把录音上传到这个通话会话，系统完成转写后自动生成通话总结。总结包含客户确认的上线窗口、需要补充的材料和仍然存在的风险。如果没有配置 ASR，录音仍可保存，但页面会显示“真实 ASR 未配置”，不会把空结果伪装成已完成转写。

聊天记录也可以单独总结。王宁在频道中点击“AI 总结”，系统只读取当前频道或私聊里他有权看到的消息。已配置 LLM 时，系统调用公司或个人模型；模型不可用时使用规则摘要，并明确显示 provider。无论哪种方式，关键要点、决定、待办和风险都可以回看。

## 第七幕：总领导只收到项目封装

周五上午，王宁确认项目汇报并发布项目级封装。封装包含完成度、风险、决策请求、更新时间和来源摘要，不包含客户项目的全部聊天原文和个人私聊。这个封装进入总领导智能体的跨项目收件箱。

总领导打开 Web 端，看到三个项目卡片：客户交付项目 82% 完成、内部平台项目 64% 完成、招聘项目存在延期风险。总领导点击“汇总全部项目”，智能体比较各项目封装，列出需要决策的事项：

- 批准客户交付项目的周五上线窗口。
- 协调内部平台项目的测试资源。
- 要求招聘项目补充延期原因和新的完成日期。

总领导看不到其他项目的原始聊天、文件和成员私聊，只能看到项目管理者智能体发布的项目摘要。这保证了跨项目上下文隔离，也让总领导得到统一、可比较的管理信息。

## 第八幕：三端同步完成闭环

晚上，王宁用微信小程序查看汇报。他能看到自己的报告、项目汇总和总领导摘要；他在“团队消息”页切换项目频道和私聊，发送一句补充说明，并点击 AI 总结。由于小程序调用的是同一组后端接口，Web 端刷新后能看到相同的消息和总结。

第二天，王宁用 Android App 打开项目。Flutter 原生壳负责启动、返回键、安全区和设备权限，业务页面通过 WebView 加载同一套 Web 工作台。页面仍然显示最新的项目选择、人轴、任务、未读消息和 AI 汇报状态。Android、iOS、Web 和小程序没有各自维护一套报告数据，因此不会出现“电脑已提交、手机仍是草稿”的分裂状态。

## 故事结束时，系统完成了什么

王宁没有手工追着每个人要周报，也没有让总领导阅读所有群聊。产品把一条工作事实从最初的任务和资料开始，沿着人轴责任链交给个人智能体，再逐级交给项目管理者智能体，最后以项目封装交给总领导智能体。

整个过程保留了人的责任和确认：

- 人轴决定谁向谁汇报。
- 权限决定智能体能看什么。
- 资料决定 AI 能说什么。
- 管理者决定冲突是否成立。
- 项目管理者决定什么内容可以上报总领导。
- 总领导根据项目封装做跨项目决策。

这就是产品的完整闭环：从登录、建公司、建项目、搭人轴、分配任务、上传资料、聊天和通话，到个人 AI 汇报、直属领导接收、项目 AI 汇总、总领导 AI 决策，再回到任务、证据和进度的实际执行。
